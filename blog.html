This primarily serves as a test post, but I wanted to write something about computing postive integer powers in $O(\log n)$ time.

The motivation for why I crossed paths with this problem was because I wanted a fast power function for computing the spectral brdf for rasterization. Since I am using C++ and $\mathtt{std::pow}$ is slow (not really, g++ will probably optimize it) I thought that writing a fast power function would be a fun challenge.

Since this function needs to be quick, recursion is out of the window. So we need some loop to do this quickly, but how? Well, let's start with a simple example: \[ x^{21} \] this is equal to \[ x^{21} = x^{16} \cdot x^4 \cdot x \] notice the binary rep of $\mathtt{21}_{10}$ is $\mathtt{10101}_{2}$ and each 1 corresponds to which power of 2 we need. To be quick the program should compute $x^{2^{i}}$ where i is the index of the ith bit of the power. To check if the ith bit is 1 shift bits right by $\mathtt{i}$ and & with 1 to get a boolean value that tells us if the ith bit is a 1. If this boolean is true, multiply $x^{2^{i}}$ with the return value. If you keep doing this until no more 1s exist in the power's binary representation you have a function that can compute powers quickly!

Although this explanation is nice and clean the way that I presented this feels disingenuous. The real way that I stumbled onto this solution, is to not notice an exponent can be made into a sum of perfect powers of two. Instead I noticed that the problem simplified greatly if the power was a power of two and worked back from there.

Since this is actually a well-known idea a common implementation looks like this: 


// this is C++, I don't know Rust 
double fastPow(double val, unsigned int exp) {
    double res = 1.0;
    while (exp > 0) {
        if (exp & 1) {
            res *= val;
        }
        val *= val;
        exp >>= 1;
    }
    return res;
}

A footnote about this function is that pow must be an unsigned int because the way that the program shifts bits. Because of two's complement, if -1 is inputted the program experiences biblical levels of overflow. You can handle this edge case with a check for negative exponent without much loss in numbers we can represent, but where is the fun in that?
